# Page cleanup preflight

Run before every site release. Use `docs/page-audit.md` for the last inventory and rationale, then inspect the current release source and build output so new routes cannot bypass the audit.

1. Inventory the active remote release separately from the local working tree: public routes, `src/pages/`, static HTML under `public/`, configured redirects, navigation/footer links, and generated sitemap URLs. A page absent from navigation can still be publicly generated or indexed. Trace dynamic routes to their full output sets. Mark each candidate as an existing remote legacy page, a retained production feature, or unfinished local work; only confirmed remote legacy pages are cleanup targets.
2. Classify candidates by purpose and evidence. Remove superseded archive views, duplicated full pages, and abandoned public experiments within the authorized scope. Preserve live user functions such as search, contact, privacy, the real 404, feeds, and verification endpoints. Preserve unfinished local pages, prototypes, assets, and uncommitted edits in place, excluding them from this cleanup release. Development prototypes should produce no production routes. Record uncertain candidates without deleting them on appearance or naming alone.
3. Give each article one canonical content page. Keep useful external historical URLs as redirects to existing canonical posts, excluding them from sitemaps and Pagefind. In this static build, `Astro.redirect` emits an HTML refresh page; do not claim an HTTP 301 unless the actual server response confirms it.
4. Remove retired page source and obsolete links, and delete components only after checking that no retained page uses them. Preserve article tags and feed metadata when deleting tag archive pages. Restore verification files to their expected token content when legacy templates have wrapped them. Update the route validator's retired-path rules and sitemap inclusion policy to match the intended public routes.
5. Run the release build, including `scripts/validate-built-routes.mjs`. Check that retired pages are absent, retained pages and redirect destinations exist, internal links resolve, sitemaps contain only canonical public pages, and search excludes redirects and retired views. Record the changes and actual validation results in `docs/page-audit.md`.
6. After installation, request the retired URLs, representative nested paths, and retained primary routes. Removed URLs should return the site's 404 response rather than old content or an unrelated homepage. Verify historical redirects reach their intended articles. If stale content remains, inspect the active release and server fallback/cache configuration before changing infrastructure. Report completion only after the live behavior matches the inventory.

Keep deployment targets and credentials in local settings described by `agent.md`; page-audit records and skill files contain no connection details or credentials.
