# Jazz 音频容量与播放评测

评测日期：2026-10-28。本轮仅在本地接入音乐；云端执行资源检查与隔离测试，没有发布音频、修改生产 Nginx 配置或安装数据库。

## 结论

当前 9 张专辑的 86 首曲目及新增的 305 个标准曲版本适合以文件形式保存，由 Nginx 提供 HTTP 分段读取；曲目名称、曲序、分类、时长及文件地址用 JSON 或数据库记录。391 个曲目入口对应 390 份独立音频（Miles Davis 的 So What 在专辑和标准曲目录复用同一文件）。全部导入资源约 3.53 GiB，现有磁盘仍有余量。32 路隔离读取测试没有出现进程内存随文件大小或并发数显著增长的现象。

本轮没有测量数据库 BLOB 接口，也没有进行跨公网、长时间播放压测，不能把下述结果当作任意数据库实现或任意网络条件下“保证不卡顿”的证明。当前机器没有检测到 PostgreSQL/MySQL 服务进程；因此没有可供比较的现成音频数据库与 Range 接口。

## Nginx 隔离测试

脚本：`scripts/benchmark-jazz-static.py`。测试创建独立的临时目录、16 MiB 合成字节文件和仅监听回环地址的 Nginx 进程；不向生产站点写文件，不开放公网端口。测试结束后停止进程并清除临时文件。

合成文件只验证文件 I/O 和 HTTP Range，并不是可解码音频。真实 M4A 的浏览器解码与切歌另外在本地播放器验证。

| 并发客户端 | Range 请求数 | HTTP 206 | P50 | P95 |
| ---: | ---: | --- | ---: | ---: |
| 1 | 8 | 全部成功 | 0.20 ms | 0.63 ms |
| 8 | 64 | 全部成功 | 1.24 ms | 3.73 ms |
| 32 | 256 | 全部成功 | 6.49 ms | 12.12 ms |

另以 32 个持续连接模拟音频读取：每连接每秒请求 32 KiB，共 12 个分块，约 262 kbit/s/人，总计 384 次请求；全部返回 206，P95 为 6.11 ms。独立 Nginx 进程 RSS 基线及 5 ms 轮询采样峰值均为 7.46 MiB；系统可用内存由 1,279 MiB 变为 1,256 MiB，其中也包含测试客户端及文件缓存的影响。

这是短时、有界、本机回环测试，证明当前文件服务路径在上述负载下没有明显的内存瓶颈。它不覆盖 TLS、公网带宽、CDN、浏览器解码、移动网络或分钟/小时级稳定性；回环吞吐不能作为对外带宽使用。

## 存储与前端方案

- 本地：原始音频与提取图片存于被 Git 忽略的 `public/jazz-local/`，曲目索引为 `src/data/jazz-local.json`。已有网站封面继续沿用。
- 前端：一份播放队列对应一个原生 `<audio preload="none">`，初始不设置 `src`，点击黑胶或曲目才指定当前音频地址。浏览器已验证初始 `src=null`、`readyState=0`，点击后才进入解码并播放。不会为 86 首歌创建 86 个音频实例，也不把音频转为 Base64/ArrayBuffer 存入 React 状态。原生音频播放后仍可按需缓冲；`preload` 是浏览器提示，并非强制网络上限。[HTML audio 文档](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/audio#preload)
- 未来云端：音频适合放在独立、持久的媒体目录或对象存储，通过 Nginx/CDN 服务；数据库只存元数据。独立目录还可避免每次站点发布都复制 0.69 GiB 音频。分段读取需验证 `206 Partial Content`、`Content-Range` 和拖动进度条。[HTTP Range 文档](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Range_requests)
- 数据库确实可以保存并流式读取大对象，但仍需要额外的应用读取和 HTTP Range 实现。本轮没有证据表明把二进制音频放数据库比静态文件更合适，因此不新增音频数据库。[PostgreSQL 大对象文档](https://www.postgresql.org/docs/current/largeobjects.html)

正式上线前应在真实音频 URL 上补测：首播等待、随机拖动后的恢复、32 路公网连续读取、站点/OpenCV 同时使用时的余量，以及响应缓存策略。当前音频没有上传到线上。

## 追加标准曲后的容量复算

| 项目 | 追加后实测 |
| --- | ---: |
| 标准曲分组 / 版本 | 15 组 / 305 个版本 |
| 曲目入口 / 独立音频文件 | 391 / 390 |
| 独立音频文件总量 | 3.498 GiB |
| 包含原图与网页缩略图的总量 | 3.528 GiB |
| 文件码率中位数 / P95 / 最大值 | 257.47 / 320.05 / 320.07 kbit/s |
| 32 人按最高码率连续收听 | 约 10.24 Mbit/s，另加协议和预缓冲开销 |

此表为本地文件统计与带宽计算，不是新增的公网并发测试。之前的持续读取模拟为每人 262 kbit/s；新增 MP3 的上限约 320 kbit/s，因此不能直接宣称已经实测 32 路最高码率播放。

音频文件数不会直接等比例增加常驻内存：分类页仅展示封面卡片、搜索和筛选，没有播放器或音频实例。点击封面进入详情页后才创建一个音频实例，并在点击播放后指定音频地址。新增版本使用原来的黑胶播放器。

Standard 封面已恢复为更高分辨率的同款原图，并接入本站统一的 WebP/AVIF 响应式压缩；列表使用 `picture/srcset/sizes` 按屏幕和像素密度选图，图片懒加载、异步解码，不向浏览器批量发送原始高清 JPEG。高清源图按图片 ID 去重为 292 个，不在每个演绎版本目录重复保存大图。

加入高清封面的压缩变体后，网页媒体合计约 3.64 GiB（音频目录 3.528 GiB，加新增压缩图 118.32 MiB）。这一容量已超过服务器操作系统可见内存，不能把整库一次性读入应用内存；但静态文件服务不要求整库常驻 RAM。更应避免每次发布都复制一份资源库：按目前空余磁盘估算，3 份完整媒体副本将占约 10.93 GiB，明显挤占余量。将音频保存为独立持久目录或对象存储，配合原生 Range 读取，比数据库全量 BLOB 查询更适合当前收藏站。

## 云端追加验收（2026-10-28）
